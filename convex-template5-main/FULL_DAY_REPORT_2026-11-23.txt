3. TECHNICAL DEEP-DIVE & ARCHITECTURAL SAFEGUARDS
----------------------------------------------------------------------------------------------------

3.1 Multi-Tenant Hardware Identification & Serial Collision Handling
In real-world enterprise deployments, multiple client organizations purchase identical off-the-shelf
biometric terminals from manufacturers (such as eSSL, ZKTeco, Matrix, Realtime). These terminals often
ship with standard or colliding factory serial numbers (e.g., BIO-001, K90-PRO-01).
If a system indexes hardware globally by serial number alone, Workspace B could hijack or overwrite
devices owned by Workspace A. IndiaPay completely eliminates this vulnerability by enforcing composite
indexing: by_workspace_serial ([workspaceId, deviceSerial]).
When webhook payloads arrive, the system resolves devices either by the explicit x-workspace-id header
or by checking for uniquely registered serials, safely rejecting ambiguous requests.

3.2 Cryptographic Secret Lifecycle & AES-256-GCM Storage
Hardware shared secrets must never reside in plaintext in the database or logs. IndiaPay implements an
enterprise cryptographic lifecycle:
1. Secret Generation: Uses crypto.getRandomValues(new Uint8Array(32)) providing 256 bits of entropy.
2. Secret Encryption: Derives a 256-bit master key from environment configuration and encrypts the secret
   using AES-256-GCM with a unique 96-bit initialization vector (iv) per device.
3. Public Redaction: Public queries (listDevices) explicitly strip secretCiphertext and secretIv.
4. Decryption on Demand: Decryption occurs exclusively in internal, sandboxed authentication routines
   (getDeviceForAuth) during live webhook validation.

3.3 Webhook HMAC-SHA256 Authentication & Timing Attack Mitigation
Biometric push webhooks authenticate every byte of the incoming payload using HMAC-SHA256. The signed
string is strictly structured as:
  signaturePayload = timestamp + "." + nonce + "." + rawBody
Using the exact raw request body guarantees that headers, JSON spacing, or payload tampering immediately
invalidates the signature.
To prevent timing side-channel attacks where an adversary measures microsecond response variances to
guess signature bytes, IndiaPay executes a constant-time comparison in Web Crypto.

3.4 Persistent Replay Attack Prevention via Atomic Nonce Claims
A valid cryptographic signature could theoretically be captured by a network attacker and replayed to
duplicate punch logs. IndiaPay implements two layers of replay defense:
1. Timestamp Freshness Window: Rejects any request where the time difference exceeds 300 seconds.
2. Atomic Nonce Claims: Every request includes a unique x-nonce. The system checks table biometricNonces
   indexed by [workspaceId, deviceSerial, nonce]. If the nonce already exists, the request is instantly
   rejected with HTTP 409 (replay_detected). If new, it is inserted with an automated TTL.

3.5 Idempotent Raw Punch Ingestion & Badge-to-Employee Resolution
Biometric hardware often retries HTTP transmissions during intermittent internet disconnects, sending the
same punch multiple times across different batches. IndiaPay guarantees transactional idempotency:
1. Deterministic Idempotency Key: Calculates a SHA-256 hash:
   idempotencyKey = SHA256(workspaceId + ":" + deviceSerial + ":" + biometricUserId + ":" + punchTimestamp)
2. Duplicate Detection: Before insertion into rawPunchLogs, the key is queried via index by_idempotency.
   If found, the existing log ID is returned with status duplicate without writing redundant records.
3. Tenant-Isolated Employee Resolution: Badge IDs (biometricUserId) are matched against employees using
   index by_workspace_employee_id. Badges assigned to employees in other workspaces are treated as
   unmapped and quarantined within the authenticated tenant workspace, preventing cross-tenant data bleed.
